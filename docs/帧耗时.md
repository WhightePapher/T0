# 帧耗时（第二轮 · Web 构建实测）

> 上一轮卡在「沙箱没有桌面显示栈，`--perf=` 跑不了」。这一轮把采集搬到线上那套构建
> （`flutter build web --profile`）上，用 headless chromium 的 CDP 跑场景、
> 读 `window.__t0perf`。**下面每个数字都是本机真实跑出来的**，原始数据在
> `docs/帧耗时_before.json`（优化前）、`docs/帧耗时_after.json`（本轮最终）、
> `docs/帧耗时_fillprobe.json`（500×900 填充率对照）。

## 0. 一句话结论

- **交互窗口没达到「帧间隔 p95 ≤ 16.7ms」**：1440×900 下 p95 = 33.3–66.7ms。
- **瓶颈不在应用代码**：UI 线程 build p95 = 8–13ms，光栅 raster p95 = 22–67ms。
  这台机器没有 GPU，headless Chromium 走 SwiftShader 软件光栅，整屏填充就是 20–60ms。
- **把视口换成 500×900（像素只有 1/3）**，同一段对比弹层的帧间隔 p50 立刻从 33.4ms
  回到 **16.7ms（60fps）**、raster p95 从 57.4 → 33.5ms —— 填充率瓶颈，不是逻辑抖动。
- **B 组的双层阴影在软件光栅下是要付钱的**：raster p95 +7~10ms（见 §3.3）。
  在 GPU 机器上这层开销可以忽略，这一条留给真机复核。

## 1. 机器、构建与口径

| 项 | 值 |
|---|---|
| CPU | AMD EPYC（4 vCPU） |
| 内存 / GPU | 7 GB / **无 GPU**（headless Chromium 154，SwiftShader 软件光栅） |
| 浏览器 | Chromium 154.0.8037.57（Debian 13） |
| SDK | Flutter 3.50.0 stable（engine bf601093） |
| 构建 | `flutter build web --profile`（release 不保证 FrameTiming 送达；profile 才有） |
| 视口 | 1440×900，DPR 1（对照跑：500×900） |
| 采集脚本 | `tool/measure_fps.py`，每场景 3 次运行，跨运行合并原始帧间隔再取分位 |

**用的是哪一套口径（不混报）**：

1. **FrameTiming（主口径）**：`SchedulerBinding.addTimingsCallback` 在 web profile 构建里
   **是回调的**（`frame_timing.supported = true`，每场景 300–1000 个样本）。
   表里的 `build_p50/p95/max`、`raster_p50/p95/max` 都是引擎上报的真实耗时。
2. **rAF 帧间隔（第二口径）**：`requestAnimationFrame` 相邻帧时间差，用来算等效 FPS 与
   「>33ms / ≥50ms 的掉帧计数」。跨运行合并后取 p50 / p95 / max。

两套各自成列，不做换算（`等效 FPS = 1000 / 帧间隔 p50`，只由第二口径推出）。

## 3. 优化：做了什么、数字怎么动

### 3.1 A3-1 对比弹层：内容先栅格化成一层，scale 只做合成

`t0DialogRoute` 的 `ScaleTransition` 里给 `child` 套了 `RepaintBoundary`；`T0Enter`
的 `Opacity/Transform` 层、页面转场层、shimmer 高光带、呼吸点也都各自成层。
意图是「动画期间只合成、不重画」。

**实测（同场景 dialog，1440×900）**：

| | 帧间隔 p95 | raster p50 | raster p95 | raster max |
|---|---:|---:|---:|---:|
| 优化前（3 次） | 66.70 | 23.40 | 57.40 | 92.20 |
| 只加 RepaintBoundary（1 次 spot check） | 66.70 | 25.80 | 61.00 | 96.40 |

**没有收益**，在噪声范围内。原因：CanvasKit 这套软件光栅不走「layer 缓存成纹理」那条路，
每帧仍然按显示列表重画；`RepaintBoundary` 在 GPU 后端是省钱的，在这里只是多切一层。
代码保留（对真机 / GPU 后端是正确的结构），但**不把它算成性能收益**。

### 3.2 A3-2 主题过渡 / shimmer / 呼吸：同样的隔离手法

主题切换窗口的 raster p50 16.7 → 17.8ms（3 次运行，噪声 ±2ms），p95 22.6 → 25.2ms。
同样是「结构对、软件光栅不领情」。抖动计数维持在个位数（6 → 10 帧 ≥50ms）。

### 3.3 A3-3 + B1 的代价：双层阴影

B1 要求单层 60px 阴影拆成 `blur 18 / offset (0,2)` + `blur 48 / offset (0,18)` 两层。
同机同场景实测，raster p95 涨了 7–10ms：

| 场景 | raster p95（单层，前） | raster p95（双层，后） | Δ |
|---|---:|---:|---:|
| 工作区操作 | 55.10 | 63.40 | +8.30 |
| 对比弹层 | 57.40 | 67.30 | +9.90 |
| 主题切换 | 22.60 | 25.20 | +2.60 |

**这是一笔明账**：软件光栅下模糊半径直接按像素算钱；GPU 后端上两层小半径阴影通常比一层大半径更便宜
（大半径模糊的采样面更大）。所以这里没有回退设计，而是把代价记在案，等真机复核。

### 3.4 A3-4 列表错峰入场：没有 20+ 控制器的问题

`T0Enter` 每张卡一个 `AnimationController` 是既有结构（工作台 2 张卡 + 模块页 5 张），
不是「一次 20+」；它每帧只重跑自己那层 `Opacity/Transform`（`AnimatedBuilder.child`），
本轮又给子树加了 `RepaintBoundary`。没有共用控制器的必要，也没改。

## 4. 没达到目标：卡在哪、试过什么、下一步

**目标**：交互态 p95 ≤ 16.7ms；重动画窗口不出现 ≥50ms 的单帧。
**结果**：p95 = 33.3–66.7ms；dialog/works 各有 143–154 帧 ≥50ms。**未达到。**

卡点证据链：

1. 同场景下 build p95 只有 8–13ms（应用逻辑、主题 lerp、重建都在预算内），
   raster p95 22–67ms —— **光栅是 2–4 倍超支的那一半**。
2. 视口从 1440×900 换到 500×900（像素数 1/3），dialog 的帧间隔 p50 从 33.4 → **16.7ms**、
   raster p95 57.4 → 33.5ms（`docs/帧耗时_fillprobe.json`）。**像素少 → 帧快**，
   是填充率瓶颈的判定性证据。
3. 加 `RepaintBoundary` / 减层级都没有改变 raster（§3.1、§3.2）——软件光栅每帧重画，
   不吃缓存。

试过、按代价排掉的：

- **RepaintBoundary 分层**（弹层 / 页面 / 入场 / shimmer / 呼吸）：已保留，收益 ≈ 0（§3.1）。
- **不在本卡改的**：缩短 420ms 主题过渡、改曲线、降低阴影规格 —— 红线禁止；
  它们能换帧数，但换的是设计。

下一步建议（按性价比）：

1. **换有 GPU 的机器复跑**：`python3 tool/measure_fps.py --label gpu`，同样一条命令。
   现在这张表只说明「软件光栅下的下限」，不能代表线上带 GPU 的浏览器。
2. **真机 Chrome（非 headless）复核**：headless 的合成器跑在 SwiftShader；
   带 GPU 的 Chrome 上 raster p95 通常掉到个位数。
3. **如果确实要守 16.7ms 且只有软件光栅**：把阴影降成单层 / 缩小模糊半径（视觉降级，
   需要你点头），或者把弹层的两页预览改成「静态图快照 + 缩放」，
   这是唯一能在填充率上真正省一半像素的做法。

## 5. 复跑

```bash
export PATH=/data/flutter/bin:$PATH
python3 tool/measure_fps.py                 # 构建 + 四场景 × 3 次，打印同样的表
python3 tool/measure_fps.py --no-build --label after   # 复用现有 build/web
python3 tool/measure_fps.py --scenarios dialog --view 500x900 --label fillprobe
```

结果同时写到 `docs/帧耗时_<label>.json`；`window.__t0perf` 里是同一份 JSON
（抓帧脚本 / DevTools 都能直接读）。桌面端仍可用 `--perf=cold|theme|works|dialog|all`
走同一套场景代码（场景实现只有一份，见 `lib/main.dart` 的 `_runPerfScenario`）。
